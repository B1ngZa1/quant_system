## T1: Token黑名单Redis持久化

### 基本信息

| 字段 | 内容 |
|-----|------|
| **优先级** | P0-高 |
| **类型** | 安全改进 |
| **预估工时** | 2.5 人天 |
| **负责人** | - |
| **关联文档** | [security.py](../../backend/app/core/security.py) |

### 问题描述

当前 Token 吊销使用内存字典 `_revoked_jti_store` 存储，服务重启后黑名单丢失。用户登出后原 Token 在过期前仍可使用，存在安全隐患。

**影响范围**：
- 安全风险：高（实盘交易场景）
- 用户体验：登出后短时间内 Token 仍可使用

### 改进方案

将 Token 黑名单从内存存储改为 Redis 存储，利用 Redis 的持久化和 TTL 特性。

**修改文件**：
- `app/core/security.py` - 修改 `revoke_token()` 和 `is_token_revoked()`
- `app/db/redis.py` - 可能需要添加 Redis 操作封装

### 实施步骤

- [ ] **Step 1** - 分析现有 Token 黑名单实现逻辑
  - 阅读 `app/core/security.py` 中 `_revoked_jti_store`、`revoke_token()`、`is_token_revoked()`

- [ ] **Step 2** - 设计 Redis 存储方案
  - Key 格式：`token:revoked:{jti}`
  - Value：过期时间戳或任意值
  - TTL：设置为 Token 剩余有效期

- [ ] **Step 3** - 实现 Redis 黑名单
  - 修改 `revoke_token()` 将 jti 写入 Redis
  - 修改 `is_token_revoked()` 从 Redis 查询
  - 保留原内存黑名单作为降级方案

- [ ] **Step 4** - 添加异常处理
  - Redis 连接失败时降级到内存黑名单
  - 记录降级事件日志

- [ ] **Step 5** - 编写单元测试
  - 测试登出后 Token 立即失效
  - 测试服务重启后黑名单仍然有效
  - 测试 Redis 不可用时的降级策略

- [ ] **Step 6** - 生产环境验证
  - 部署后验证 Token 吊销功能

### 验收标准

| 指标 | 目标值 |
|-----|-------|
| Token 登出后失效延迟 | < 100ms |
| 服务重启后黑名单有效性 | 100% |
| Redis 不可用时降级 | 成功降级到内存 |

### 回滚策略

保留原内存黑名单代码，添加 Feature Flag 控制使用 Redis 还是内存实现。

### 测试计划

| 测试类型 | 测试用例 |
|---------|---------|
| 单元测试 | `test_revoke_token_immediate_effect` |
| 单元测试 | `test_revoke_token_persistence_after_restart` |
| 降级测试 | `test_redis_unavailable_fallback_to_memory` |

## T3: 缓存层完善与监控

### 基本信息

| 字段 | 内容 |

| **关联文档** | [cache_helper.py](../../backend/app/utils/cache_helper.py) |

### 问题描述

Redis 配置存在但未充分利用，高频查询（股票行情、用户信息）直接打数据库。缺少缓存命中率监控。

**影响范围**：
- 性能风险：中
- 数据库负载：高

### 改进方案

1. 识别高频查询场景
2. 实现 Cache-Aside 缓存模式
3. 添加缓存监控指标

### 实施步骤

- [ ] **Step 1** - 识别高频查询
  - 分析 API 日志，识别 Top 10 高频查询
  - 确定适合缓存的场景（股票行情、用户信息、策略列表）

- [ ] **Step 2** - 设计缓存策略
  - Stock行情：TTL = 10s（实时性要求高）
  - 用户信息：TTL = 5min（低频变化）
  - 策略列表：TTL = 1min

- [ ] **Step 3** - 实现缓存工具类
  - 扩展 `app/utils/cache_helper.py`
  - 提供 `@cached` 装饰器

- [ ] **Step 4** - 应用缓存到高频 API
  - `GET /stock/realtime` - 股票行情
  - `GET /user/info` - 用户信息

- [ ] **Step 5** - 添加监控埋点
  - 缓存命中/未命中计数
  - 记录到 Prometheus/日志

- [ ] **Step 6** - 压测验证
  - 使用 locust 对比缓存前后 QPS
  - 验证数据库 QPS 降低

### 验收标准

| 指标 | 目标值 |
|-----|-------|
| 缓存命中率 | > 70% |
| 数据库 QPS 降低 | > 30% |
| API P99 响应时间降低 | > 20% |

### 回滚策略

配置开关 `CACHE_ENABLED=false` 控制缓存启用/禁用。

### 测试计划

| 测试类型 | 测试用例 |
|---------|---------|
| 功能测试 | `test_cache_hit_return_cached_data` |

- [ ] **Step 3** - Numba JIT 优化
  - 分析信号计算热路径
  - 使用 `@numba.jit` 装饰器

- [ ] **Step 4** - 架构优化（可选）

  - 按标的拆分任务

- [ ] **Step 5** - 压测验证

### 验收标准

| 单标的回测性能提升 | > 50% |
