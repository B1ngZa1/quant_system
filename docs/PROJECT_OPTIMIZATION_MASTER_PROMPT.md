## 二、优化目标 A：后端响应速度与可扩展性

### 2.1 总体原则

- **可测量**：任何优化须附带优化前后的对比数据（同一环境、可复现的请求集合）。
- **先瓶颈后微优化**：先用 profiling / 慢查询日志定位热点，再改索引与缓存。
- **读多写少场景优先缓存与只读副本**；写路径保持事务边界清晰。

### 2.2 数据库与持久层

| 方向 | 具体要求 |
|------|----------|
| **索引** | 对高频 `WHERE` / `JOIN` / `ORDER BY` 字段审查 `EXPLAIN`；`stock_data(symbol, trade_date)`、`stock_realtime(symbol)`、`stock_basics(symbol)` 等须与真实查询一致；避免全表扫描。 |
| **查询形态** | 列表接口使用分页 + 必要字段投影；禁止 `SELECT *` 大表；N+1 查询改为 `joinedload` / 批量查询或单条聚合 SQL。 |
| **连接池** | 校验 SQLAlchemy/async 池大小与 MySQL `max_connections`；避免在请求中长时间占用连接。 |
| **迁移与一致性** | 新增索引通过 Alembic 迁移；生产变更需可回滚说明。 |

**参考指标（需在压测或 staging 上给出）：**

- P95 延迟：核心列表类 API 在「Warm cache」下 **< 200 ms**（单机、局域网，具体以当前基线 ±30% 为改进目标亦可接受，但须写明基线）。
- 单次列表查询 DB 往返：**≤ 2～3 次**（含 count + 分页数据）。

### 2.3 接口层（FastAPI）

| 方向 | 具体要求 |
|------|----------|
| **异步** | I/O 密集路径使用 `async`；阻塞型第三方库用 `asyncio.to_thread` 并控制并发。 |
| **序列化** | 大列表响应考虑分页默认上限；必要时压缩（已有 GZip 中间件则校验阈值）。 |
| **依赖注入** | DB Session 生命周期与异常时正确关闭；避免在循环中重复创建昂贵对象。 |

### 2.4 缓存策略

| 层级 | 内容 |
|------|------|
| **进程内 TTL** | 已有 `DataEngineService` 类 TTL 缓存：评估 TTL 与键粒度，避免缓存击穿（热点 key 可短 TTL + 单飞）。 |
| **Redis** | 对「行情列表、市场概览」等读多接口：统一 `cache key` 规范、过期时间、以及数据源变更时的失效策略（或较短 TTL + 定时预热）。 |
| **HTTP** | 对静态或半静态资源考虑 `Cache-Control`（若经 Nginx/CDN）。 |

**参考指标：**

- 命中 Redis 或进程内缓存时，对应接口 P95 **较无缓存下降 ≥ 50%**（相对当前实现测量）。

### 2.5 观测与回归

- 关键路径打结构化日志（耗时、来源：`local_db` / `akshare` 等）。
- 可选：为 `/api/v1` 下高频路由增加简单 metrics（请求数、延迟直方图），便于回归对比。

## 三、优化目标 B：前端首页与整体体验

### 3.1 对齐参考首页的实施步骤

1. **对照阅读**：打开参考 `HomeView.vue` 与当前 `dashboard/index.vue`，列出组件区块差异表（行情条 / 卡片 / 图表 / 侧边模块）。
2. **样式令牌**：抽取参考中的间距、字号、颜色变量，在 `frontend` 中集中到 CSS 变量或主题配置，避免魔法数散落。
3. **组件复用**：能拆则拆（如 `MarketTicker`、`StatCards`、`ChartCard`），保证后续页面一致。
4. **数据对接**：保持与现有 `api` 封装一致；新增字段需后端配合时在「协作」节登记契约。
5. **响应式**：断点建议 `≥1280` 桌面完整布局、`768～1279` 压缩侧栏或堆叠、窄于 `768px` 时单列与可折叠行情条；图表使用 `resize` 监听或容器 `ResizeObserver`。
6. **加载性能**：路由级 `defineAsyncComponent` 或等价懒加载重页面；图表库按需引入；首屏仅请求必要接口，非首屏模块 `IntersectionObserver` 或二次进入再拉取。

### 3.2 前端技术指标（建议）

| 指标 | 目标 |
|------|------|
| **LCP（首屏）** | 在开发机 Chrome 性能面板或 Lighthouse：相对优化前 **改善 ≥ 20%**，或 LCP **低于 2.5s**（弱网另计） |
| **JS 体积** | 首页相关 chunk 无无理由膨胀；新增依赖需说明必要性 |
| **CLS** | 骨架屏与内容切换时布局无明显跳动（预留高度） |

### 3.3 评估标准（前端）

- [ ] 与参考首页在**区块顺序与视觉权重**上无明显偏差（评审用并排截图）。
- [ ] 移动端可用性：无横向溢出、触控目标足够大。
- [ ] 深色/浅色（若项目支持）对比度可读。
- [ ] 无控制台报错；网络失败时有用户可理解的提示。

## 四、前后端协作要求

| 事项 | 说明 |
|------|------|
| **API 契约** | 首页所需字段以 OpenAPI / 接口文档为准；字段增减走评审，版本化或向后兼容。 |
| **分页与筛选** | 前端分页参数与后端默认值一致；避免一次拉全市场列表。 |
| **缓存语义** | 前端展示「数据时间」若依赖 `last_update`，后端须在响应中稳定返回。 |
| **联调环境** | 约定 baseURL、CORS、以及是否使用 mock；性能测试尽量接近生产数据量。 |
| **缺陷归属** | 慢接口先由后端提供 trace/日志；前端先排除重复请求与瀑布流请求。 |

## 五、实施步骤（建议顺序）

1. **基线**：记录当前 Lighthouse / wrk 或 hey 压测结果、MySQL 慢查询日志（若有）。
2. **后端**：索引与 SQL → 热点接口缓存 → 异步与连接池调参。
3. **前端**：首页布局对齐参考 → 样式令牌 → 懒加载与图表优化。
4. **联调**：同一分支内完成接口与 UI 对齐，避免长期分叉。
5. **验收**：按第六节检查清单签字（或 PR 描述中勾选）。
